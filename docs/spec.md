# LightBee 規格書

> 版本：0.1
> 最後更新：2026-09-04
> 狀態：草稿
> 內部代號：WCALSS（repo、命名空間、既有雛型沿用）

---

## 1. 專案概述

LightBee 是一個 Windows 系統匣常駐工具，用一般 USB／內建網路攝影機當作粗略的環境光感測器，依環境明暗把螢幕亮度自動調到三個預設檔位之一。它解決的是「桌機或外接螢幕沒有硬體環境光感測器、Windows 的自動亮度因此完全無法使用」的情況：使用者在關燈的房間裡，螢幕維持白天的亮度會刺眼，得手動去調。目標使用者是有網路攝影機、願意安裝未簽章工具並切換一個 Windows 相機設定的桌機／擴充底座使用者。

本專案建立在 `spike/` 與 `app/WcalssAmbientBrightness/` 已完成的 spike 與端對端雛型之上（見 `docs/spike-report.md`），把已驗證的「相機讀值 → 分級 → 漸進調光」流程產品化。

---

## 2. 核心問題

沒有硬體環境光感測器的 Windows 桌機（以及接了外接螢幕、內建感測器用不上的筆電），無法使用 Windows 內建的自動亮度。使用者只能手動調整螢幕亮度，而多數人不會頻繁去調——結果是關燈後螢幕過亮刺眼、白天又可能不夠亮。市面上的替代方案要嘛需要額外購買硬體感測器，要嘛是付費軟體。

spike 已證明（`docs/spike-report.md` §12.5）：在關燈情境下，用網路攝影機讀值自動把螢幕從 80% 漸進降到 15%，使用者主觀回饋「暗很多，眼睛比較舒服，不用自己調」。核心問題是可解的，缺的是把雛型變成可散布、可長時間穩定執行的產品。

---

## 3. 目標

本專案必須達成：

1. **背景常駐、低干擾地偵測環境明暗**：週期性 Lazy 取樣（不長時間佔用相機），把全畫面平均亮度分類到三個粗略區間（暗／微光自然光／有開燈），並用遲滯、連續兩次確認、自適應 EMA 濾除單次突波與邊界抖動。
2. **自動、漸進地調整螢幕亮度**：依分級目標值，透過 WMI／ACPI（優先）或 DDC/CI（備援）寫入螢幕亮度，且以速率限制的方式逐步逼近目標（變亮快、變暗慢），不是一次跳階。
3. **對使用者的手動調整讓步**：偵測到使用者自己動了螢幕亮度時，暫停自動寫入，把控制權交還給使用者一段時間。
4. **長時間穩定執行並能自我恢復**：偵測到連續取樣失敗時自動重建相機工作階段，不需使用者手動重啟；已知的系統層級相機共用卡死（`docs/spike-report.md` §13.4）在 App 能力範圍外，需明確告知使用者復原方式。
5. **可散布、可驗證**：單一自帶執行環境的 exe、可放入啟動資料夾開機自啟；每一次判定寫入可回溯的驗證紀錄；內建 `--selftest` 演算法自檢維持綠燈。

## 4. 非目標

本專案不包含：

- **取代硬體環境光感測器或 Windows 自動亮度**：這是粗略的三段式輔助工具，不是等效替代品。
- **連續或多級調光**：spike 的 Gate B 判定為 PARTIAL——`normal`／`bright` 沒有被數據證實是兩個不同等級。僅提供三段，不假裝能做漸進亮度刻度。
- **內容感知／逐 App 亮度**：不會因為前景視窗是什麼而改變行為。
- **色溫、Night Light、藍光濾除**：只碰亮度百分比。
- **逐螢幕獨立亮度**：多螢幕一律套用相同百分比（見 §6）。
- **跨平台**：Windows 專屬（相機、亮度控制、格式協商全綁 Windows API）。
- **多使用者、雲端同步、遙測**：設定與紀錄只存在本機。
- **校準到真實 lux**：讀值是相對量，不做物理單位校準。
- **修復系統層級的相機共用卡死**：`docs/spike-report.md` §13.4 記錄的 FrameServer 壞死只能由使用者手動關開「相機共用」設定或重插 USB 解決，App 無法自我恢復。
- **v1 不含 Palladio 風格的 WebView2 設定介面**：v1 用 WinForms，預留遷移路徑（見 §6）。

## 5. 功能清單

### Must-have（MVP 必要）

多數項目已在 `app/WcalssAmbientBrightness/` 雛型實作並於使用者本機驗證過（見 `docs/spike-report.md` §12–§15）。

- [ ] 系統匣常駐圖示：顯示目前分級與讀值、啟用／停用自動調整、立即取樣一次、開啟設定、結束。
- [ ] 週期性 Lazy 取樣迴圈：預設 5 秒間隔，每次 Open→Sample（略過 ~550ms 曝光收斂期，收斂後可提前結束）→Release。
- [ ] 三段亮度分級 + 遲滯 + 連續兩次確認：預設門檻取自 spike Test 06 實測（暗 <0.01、微光 <0.20、有開燈以上），對應目標亮度 15% / 45% / 80%，皆可在設定中調整。
- [ ] 自適應 EMA 平滑：小擾動 α=0.5，大幅變化（|raw−ema|≥0.1）α=0.9 並保留一次尾窗。
- [ ] 漸進亮度控制：目標值與實際寫入值分離，200ms 速率限制器逼近（變亮 15%/秒、變暗 8%/秒）。
- [ ] **自適應取樣節奏**（`SamplePacing`，已實作，**發布前須完成真機端對端驗證**，見 §7 發布前門檻）：讀值與平滑值差距 ≥0.03、或任一值距分級邊界 ≤0.05 時，把下一輪間隔縮到 500ms；讀值回穩立即退回慢間隔；快模式最多連續 30 輪後強制一輪慢取樣；任何取樣失敗立即退回慢間隔。
- [ ] 亮度控制雙路徑：WMI／ACPI 優先，失敗自動退到 DDC/CI（`dxva2.dll` P/Invoke），反之亦然。
- [ ] **手動亮度讓步**：
  - 每輪取樣讀取螢幕目前實際亮度，與 App 最後一次寫入值比對。
  - 差距超過門檻（預設 5%）且非來自自身漸進過程 → 進入「讓步」狀態：停止寫入亮度，但持續取樣與分級。
  - 退出讓步（先到者）：(a) 分級從進入讓步時的分級變動；(b) 可設定的冷卻時間到期（預設 15 分鐘）；(c) 使用者按「立即取樣」或切換啟用開關。
  - 系統匣狀態顯示「已暫停（使用者手動調整）」。
- [ ] 相機工作階段自動重連：連續 3 輪取樣失敗時重建 `AmbientLightSensor`，並寫入紀錄。
- [ ] 動態格式協商：優先 640×480/NV12/30fps，共存情境下退到可用清單中最高解析度的 NV12。
- [ ] `SharedReadOnly` 為預設相機共用模式（spike Test 10：起始讀數比 `ExclusiveControl` 穩定）。
- [ ] 設定視窗（WinForms）：相機裝置名稱、共用模式、取樣間隔、遲滯區間、可編輯的分級表、讓步冷卻時間、即時狀態、驗證紀錄檢視、紀錄檔路徑。
- [ ] 驗證紀錄：每次「取樣→判定→套用」寫一筆 CSV 到 `%AppData%\LightBee\validation-log.csv`，含回溯到 spike Test 的標註；檔案 I/O 失敗不影響執行。
- [ ] 設定持久化：`%AppData%\LightBee\config.json`，載入時對數值範圍做 clamp。
- [ ] 開機自啟開關：於啟動資料夾建立／移除指向 exe 的捷徑，每次啟動校正捷徑路徑。
- [ ] 相機初始化失敗的明確提示：區分「需開啟 Windows 相機共用設定」（`SharedReadOnly` 會丟 `0x80070020`）與「裝置被 `ExclusiveControl` 佔用」等情況，並在氣泡通知附上處理指引（含設定路徑：設定 → 藍牙與裝置 → 相機 → 目標相機 → 進階相機選項 → 編輯 → 允許多個應用程式同時使用相機）。
- [ ] `--selftest` 演算法自檢：維持 19/19 綠燈，可用於 CI 或接手驗證。
- [ ] 資料夾遷移：若偵測到舊雛型的 `%AppData%\WCALSS\AmbientBrightness\`，一次性搬移到 `%AppData%\LightBee\`。

### Nice-to-have（後續可加）

- [ ] Palladio 風格的 WebView2 設定介面（取代 WinForms 設定視窗；托盤殼維持原生）。
- [ ] 相機擺放引導：首次執行時提示把相機抬高、避開直視螢幕與窗戶（spike §14.7 證實角度是關鍵變因）。
- [ ] 「微光」分級的主觀驗證與可能的門檻／目標值微調（spike §12.6：這一段從未有使用者回饋確認；目前無法測試，照現值出）。
- [ ] 相機共用操作節流：避免高頻率搶相機觸發系統層級卡死（spike §13.4）。
- [ ] 驗證紀錄的匯出／歸檔機制。
- [ ] Discord／瀏覽器／OBS 共存實測後可能的相容性調整。

## 6. 技術考量

- **語言 / 框架**：C# / .NET（出貨時對 net10 LTS，TFM 保留 `net10.0-windows10.0.19041.0`）。UI v1 用 WinForms（托盤 `NotifyIcon` 內建、有 `ShowBalloonTip`；設定視窗手刻）。設定視窗設計成薄的可替換層（乾淨的 C# 設定／狀態 API），預留之後換 WebView2 + Palladio（Palladio 是 CSS token 系統，web UI 可直接複用 `palladio.css`）。**不使用 Wails v2**（會強制改用 Go、須重做 WinRT 相機 interop）。
- **平台**：Windows 10 1809+ / Windows 11。相機共存需要 Windows 11 2025-03 更新（KB5052093）加入的「允許多個應用程式同時使用相機」逐裝置設定；未開啟時，`SharedReadOnly` 會立即失敗（可偵測），`ExclusiveControl` 則安靜收不到 frame。沒有其他 App 同時使用相機時，不需要這個設定。
- **多螢幕**：對所有可控螢幕套用相同亮度百分比。DDC/CI 讀取時取多螢幕平均值顯示；WMI 路徑控制 ACPI 內建面板。不提供逐螢幕獨立設定。
- **外部依賴**：
  - WinRT（`Windows.Media.Capture` / `MediaFrameReader`、`Windows.Devices.Enumeration`）——改用正規 targeting pack 投影，移除目前的 preview 版 `Microsoft.Windows.SDK.NET`（消除 `WinRT.Runtime` 版本衝突警告）。
  - `System.Management`（WMI `root\wmi` 亮度控制）。
  - `dxva2.dll` P/Invoke（DDC/CI）。
  - WebView2 執行階段——僅在採用 web UI 後才需要；為「單一 exe、無相依」目標上的已知取捨。
- **散布**：單一 self-contained 單檔 exe（`PublishSingleFile` + `SelfContained` + `IncludeNativeLibrariesForSelfExtract`），預估 60–90MB；trimming 待實測（WinRT interop / 反射可能被破壞）。**無程式碼簽章**——接受 SmartScreen 首次執行警告與防毒誤判風險，於下載頁提供執行步驟與 SHA256；日後可評估 SignPath.io（OSS 免費）或 Azure Trusted Signing（約 US$10/月）。散布通路：GitHub Releases，之後可能加專案網站。
- **限制**：
  - 相機佔用須維持低檔（spike Test 09：Lazy 模式約 3% CPU/Wall）；自適應快取樣不得抬高長期平均佔用。
  - 不對疑似故障或被搶占的相機連續高頻開關（spike §13.4 教訓）。
  - 全畫面平均亮度作為訊號，前提是相機視野內看不到螢幕自身光線或明顯反射（spike §14）——這是使用者端擺放責任，App 只能引導不能強制。

## 7. 成功指標

- **反應時間**：關燈後，平滑值在 ≤ 3 次取樣（預設約 15 秒）內跨進「暗」區間，螢幕於漸進調整理論時間內（例：80%→15% 約 8 秒）到達 15%；開燈同理到達 80%。
- **抗突波**：螢幕上出現持續 < 10 秒的亮內容（通知、切視窗）不造成分級切換；`--selftest` 的雙重確認／遲滯／突波回復案例維持通過。
- **手動讓步**：使用者手動改亮度後，App 於下一輪取樣內停止寫入並顯示暫停狀態；冷卻期滿或分級變動後恢復自動調整。
- **相機佔用**：長時間執行的平均 CPU/Wall 佔用與 spike Test 09 的 Lazy 基準（~3%）同量級；啟用自適應取樣後長期平均不顯著上升。
- **穩定性**：連續執行 ≥ 4 小時不出現「需手動重啟 App」的卡死；App 層級取樣中斷能由自動重連恢復並留下紀錄。系統層級相機共用卡死不計入（App 能力外），但須有明確使用者提示。
- **正確性回溯**：`validation-log.csv` 每筆都能對應到 spike 報告的某個 Test／Gate 結論。
- **主觀**：關燈情境下使用者回報螢幕不再刺眼、不需手動調整（重現 spike §12.5 的結果）。
- **發布前門檻**：2026-09-04 新增的自適應平滑／快取樣／提前結束功能完成真機「取樣→分級→漸進調光」端對端驗證，具體確認 `docs/spike-report.md` §15.4 列的三項：(1) 關燈／開燈後能在可接受時間內到達既有三段目標且不誤切換；(2) 快模式結束後退回慢間隔、長時間執行不引發相機共享卡死；(3) §14.7 已驗證的相機角度下，螢幕白色內容仍不污染輸入訊號。

## 8. 開放問題

以下事項尚未確認，需後續測試或設計決策；不阻擋 v1 起步，但應在 spec 補強或轉為 GitHub Issue 時處理。

1. **spike 未完成的測試項**：Test 07（ROI 取樣能否繞開自動曝光全域補償）、Test 10 其餘 App（Discord／瀏覽器／OBS 共存）、Test 11（Busy Handling）、Test 12（Privacy Permission UX）、Test 13（USB 熱插拔）、Test 14（睡眠／喚醒後恢復）。
2. **相機擺放角度／窗戶反光**對訊號乾淨度的系統性測試（spike §14.6／§14.7 只驗證了單一新角度）。
3. **相機共用高頻操作節流**的具體設計與門檻（spike §13.4）。
4. **手動讓步的參數**：5% 偵測門檻與 15 分鐘冷卻是初始猜測，需真機調校；漸進過程中如何可靠區分「自身寫入造成的差距」與「使用者調整」。
5. **睡眠／喚醒、顯示器熱插拔**後的重新初始化流程（對應 Test 13／14）。
6. **驗證紀錄長期歸檔方式**（目前只在 `%AppData%`，不在版控）。
7. **未簽章散布的使用者引導文案**（SmartScreen「仍要執行」、防毒誤判、SHA256 對照）。
8. **「微光」中段**目前無環境可測（使用者無筆電、難以營造純自然光場景），照現值出貨，待日後有條件再驗證。
