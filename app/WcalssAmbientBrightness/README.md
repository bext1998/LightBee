# WCALSS 環境光自動亮度（背景常駐 App）

這不是新的 Spike 測試，是把 `spike/camera-probe` 已驗證過的行為，接成一個真的會跑的產品雛型，用來確認「Spike 測過的項目在實際使用情境下真的能用」。

## 這個 App 做什麼

- **背景常駐**：以系統匣（Tray）圖示執行，右鍵選單可開啟設定、立即取樣、切換自動調整開關、結束程式。
- **週期性偵測環境光**：預設每 5 秒 Open → Sample → Release 一次（對應 Test 08 驗證過的 Lazy 模式長時間穩定性），略過每次取樣開頭約 0.55 秒的曝光收斂期（對應 Test 04/05 實測收斂時間）才計算平均亮度。
- **三段式自動調整螢幕亮度**：只做「暗／微光自然光／有開燈」三段，**不做連續調光**——因為 Gate B 的結論明講 `normal`/`bright` 兩個亮度段位測不出差異，做出連續調光介面等於展示一個沒被驗證過的能力。每段的判斷邊界都能在設定視窗調整，並標註對應到 `docs/spike-report.md` 的哪個 Test。
- **Sharing Mode 預設 `shared`（SharedReadOnly）**：對應 Test 10 的發現——這個模式的起始亮度讀數比 `exclusive` 更穩定。使用者仍需自行確認 Windows「相機共用」系統設定是否開啟（Test 10 已知的前提條件，App 無法自己解決）。
- **螢幕亮度控制先走 WMI（`WmiMonitorBrightnessMethods`），後備 DDC/CI**：WMI 控制支援 ACPI 的內建面板；沒有 WMI 時，程式透過 `Dxva2.dll` 的 DDC/CI API 控制支援 DDC/CI 的外接螢幕。兩種方式都不可用時，設定視窗會如實顯示原因。
- **驗證紀錄**：每一次取樣循環都寫一筆紀錄（原始亮度、判定分級、是否套用了新亮度、對應哪個 Gate/Test），存在設定視窗的「驗證紀錄」分頁，以及：

  ```text
  %AppData%\WCALSS\AmbientBrightness\validation-log.csv
  ```

  這是回應「確認測過的項目都能被驗證」這個目的的核心機制：不只是程式跑起來，而是每一次自動調整都能回溯到 Spike 報告裡具體哪一筆實測結論。
- **漸進式亮度調整**：分級判定出來的目標亮度不會直接套用，而是用速率限制器逐步逼近（變亮每秒最多 15%、變暗每秒最多 8%），加上判定前的 EMA 平滑，減少相機自動曝光單次抖動造成的誤判。細節與實測數據見 `docs/spike-report.md` 第 13 節。
- **自適應取樣節奏與自適應平滑（回應「環境亮度感知太慢」，尚未真機端對端驗證）**：原本固定 5 秒取樣 + 固定 α=0.5 的 EMA，關燈這種大幅轉換要 7 次以上取樣才能追上（實際體感約 30 秒以上才開始變暗）。現在改成：
  - 取樣間隔自適應：讀值穩定且遠離分級邊界時維持 5 秒（Gate C 低佔用不變）；讀值大幅變化或逼近分級邊界時縮短到 500ms，讓「以取樣次數計」的防抖機制（EMA 收斂、連續兩次確認）在時間軸上自動縮短。快模式有次數上限（超過強制一輪慢取樣），取樣失敗立刻退回慢間隔，避免 13.4 節的高頻相機操作風險。
  - EMA 自適應：小幅擾動維持 α=0.5 防抖；大幅變化（|raw−平滑值| ≥ 0.1）改用 α=0.9 並持續一次尾窗，兩三次取樣（快模式下約 3-5 秒）就追上真實變化。分級切換的「連續兩次確認」與遲滯機制不變，防單次突波與螢幕回饋的保護沒有被削弱。
  - 取樣窗提前結束：窗內收斂期後的讀值一穩定（沿用 Test 04/05 的 max−min ≤ 0.01 判定）就提前結束取樣，不必每次等滿 1.2 秒。
  - 相關參數可在 `%AppData%\WCALSS\AmbientBrightness\config.json` 調整（`AdaptiveFastIntervalMs`、`AdaptiveDeltaThreshold`、`AdaptiveBoundaryMargin`、`AdaptiveMaxFastCycles`），設定視窗尚未加入這些欄位。
- **相機工作階段自動重連**：連續 3 輪（約 15 秒）取樣都拿不到畫面時，自動重建相機工作階段，不用整個 App 重啟。這只能處理「這個 App 自己的連線卡住」，處理不了 Windows 相機共用機制本身在系統層級卡死的情況（見下方「已知限制」與報告第 13.4 節）。

## 建置與執行

在本目錄執行：

```powershell
dotnet build
dotnet run
```

單元測試直接內建在本專案（`SelfTest.cs`，維持單一資料夾結構），以下列方式執行（不會開相機，純驗證演算法邏輯，exit code 0 = 全部通過）：

```powershell
dotnet run -- --selftest
```

執行後不會有主視窗，請到系統匣找 WCALSS 圖示。雙擊圖示或右鍵「開啟設定…」可以看到：

- **設定**分頁：裝置名稱、Sharing Mode、取樣間隔、遲滯區間、三段亮度分級與對應驗證來源。
- **即時狀態**分頁：目前讀數、目前分級、目前使用的亮度控制方式（WMI／ACPI 或 DDC/CI）。
- **驗證紀錄**分頁：逐筆取樣歷史，可直接對照 Spike 報告核對結論是否成立。

## 已知限制（誠實對照 Spike 報告，不是這個 App 沒做完）

- **只有三段亮度分級**：這是 Gate B「PARTIAL」判定的直接後果，不是實作偷懶。要做更細的漸進分級，需要先用可控漸進光源（如可調光檯燈＋Lux 計）重新驗證 Test 06，這超出本輪範圍。
- **不支援 DDC/CI 的外接螢幕無法自動調整**：螢幕 OSD 內的 DDC/CI 開關、轉接器與 KVM 都可能讓 `GetMonitorBrightness`／`SetMonitorBrightness` 不可用；App 會保留取樣與分級紀錄，並在即時狀態列出控制器回報原因。
- **相機共用系統設定仍需使用者手動開啟**：Test 10 已證實這是 Windows 層級的前提條件，App 偵測不到、也改不了這個設定本身。
- **Discord／瀏覽器／OBS 等其他相機 App 的共存情境尚未驗證**：Spike 報告只測過與 Windows 相機 App 共存，這個 App 沿用同一套邏輯，但沒有针對其他 App 重新測過。
- **相機共用機制本身在高頻率搶奪或長時間運作下可能系統層級卡死，App 自己無法復原**：實測發現過（見報告 13.3、13.4 節）反覆搶奪相機控制權可能讓 Windows 的相機共用狀態壞掉，連全新程序都拿不到畫面，此時 App 內建的自動重連沒有用，需要使用者手動關掉再打開「相機共用」系統設定，或拔插 USB 相機。

## 與 spike/camera-probe 的關係

`AmbientLightSensor.cs` 裡的裝置列舉、格式選擇（含 640x480/NV12 → fallback 最高解析度 NV12）、NV12 Y-plane 平均亮度計算，都是直接從 `spike/camera-probe/ColdStartCommand.cs` 移植過來的同一套邏輯，只是把「重複 N 輪後結束」的一次性測試迴圈，改成用 `System.Windows.Forms.Timer` 驅動的無限背景迴圈。這樣才能確保「這個 App 觀察到的行為」跟「Spike 報告記錄的行為」是同一套實測依據，不是另外重新猜一套。
